## 1. 개발 중 실제로 겪은 문제

### 1-1. 다른 장치는 되는데 CLCD에만 글자가 안 나옴 → 패킷 끝 판별 방식 수정

| 항목 | 내용 |
|---|---|
| 현상 | 88-2를 보드에 올리고 앱과 통신은 되는데, 앱에서 보낸 문자열이 CLCD에 **한 글자도** 나오지 않음 |
| 확인 방법 | 수신 콜백이 모은 패킷을 Tera Term에 **16진수로 찍어** STX부터 ETX까지 제대로 모이는지, 어디서 끊기는지 직접 확인하며 원인을 좁힘 |
| 하드웨어 배제 | 같은 보드에 이전 버전 `88.EVB_DEMO2_led_parsing`을 올리면 CLCD를 포함해 W 기능이 모두 정상 → 전원(E5V), 대비(VR1), 배선은 원인이 아님 |
| 비교 | 두 프로젝트의 `clcd.c`, `clcd.h`, `main.h`는 동일. 다른 곳은 두 군데: ① USART1 수신 콜백의 **패킷 끝 판별**, ② CLCD 문자열 복사 루프 |
| ① 패킷 끝 판별 | 88-2는 **처음 들어온 0x03**을 ETX로 보고 패킷을 끝냄. 88은 **DATASIZE(`rx_buffer1[3]`)로 ETX 위치를 계산**하는 방식이었고, 예전 0x03 방식은 주석으로 남아 있었음. 문자열에는 0x03이 거의 없지만, 엔코더 값·float 바이트처럼 이진 DATA에는 0x03이 들어갈 수 있어 구조적으로 위험한 방식 |
| ② 복사 루프 | `for (i = 15; i > 0; i--)` → 16글자 중 15글자만 복사 (아래 이슈 7) |
| 수정 | ① 88의 길이 기반 판별을 옮기되, **ETX 자리까지 다 받은 순간에만** ETX를 확인하도록 고침. 88 방식은 매 바이트마다 `rx_buffer1[packet_length]`를 읽어, 같은 길이의 패킷을 연속으로 보내면 **이전 패킷의 ETX**를 보고 미리 완료 처리할 수 있었음. ETX 자리가 0x03이 아니거나 길이가 버퍼(50바이트)를 넘으면 버리고 STX부터 다시 받음 ② `i >= 0`으로 16글자 복사 |
| 결과 | 수정 후 보드 테스트에서 CLCD 1·2줄 정상 표시 (2026-11-20) |
| 한계 | ①과 ②를 함께 고쳐 해결했기 때문에, 둘 중 어느 것이 "한 글자도 안 나온" 직접 원인이었는지는 하나씩 되돌려 보는 시험을 하지 않아 단정하지 않음 |

```c
// main.c : HAL_UART_RxCpltCallback (USART1) — 수정 후
rx_buffer1[rx_index1++] = rx_data1;
if (rx_index1 >= 4) {
    if (calculate_cout == 0) {
        packet_length = rx_buffer1[3] + 4;            // ETX가 있어야 할 인덱스
        calculate_cout = 1;
        if (packet_length >= sizeof(rx_buffer1)) { rx_index1 = 0; calculate_cout = 0; }
    }
    if ((calculate_cout == 1) && (rx_index1 == packet_length + 1)) {   // ETX 자리까지 다 받음
        if (rx_buffer1[packet_length] == 0x03) RX_flag1 = 1;
        else rx_index1 = 0;                           // 형식 오류 → 다시 STX부터
        calculate_cout = 0;
    }
}
```

**배운 점:** 바이너리 데이터가 실리는 프레임에서 "특정 값이 오면 끝"은 데이터와 구분자가 겹칠 수 있다. 길이 필드가 있는 프로토콜이면 **길이로 끝 위치를 정하고, 그 자리에서 ETX를 검증**하는 쪽이 안전하다. 또 차이점을 한 번에 고치면 결과는 좋아도 원인이 흐려진다 — 하나씩 바꾸며 확인했다면 원인을 정확히 짚을 수 있었다.

### 1-2. 88에서는 되던 RGB LED 제어가 88-2에서 안 됨 → 해석이 끝날 때까지 수신 보류

| 항목 | 내용 |
|---|---|
| 현상 | 1-1 수정 후 CLCD는 정상인데, 앱에서 RGB LED 색을 바꿔도 반영되지 않음. 같은 보드에서 88은 정상 |
| 설정 비교 | `MX_TIM3_Init`(PSC 63, center-aligned, ARR 255), `stm32f1xx_hal_msp.c`(PC6/7/8 AF, TIM3 full remap), `main.h` 핀 정의, `case RGBLED` 처리가 88과 **모두 같음** → RGB 코드가 아니라 88-2에만 있는 부분이 원인 |
| 원인 | 88-2는 R 기능 때문에 메인 루프 1회가 길다 (HDC1080 측정 `HAL_Delay(15)` + R 패킷 블로킹 송신, 최소 약 16 ms). 9600 bps에서 RGB 패킷(8바이트)은 약 8 ms마다 도착할 수 있어, 앱이 색을 연달아 보내면 **이전 패킷을 해석하는 중에 다음 패킷이 들어옴**. 그런데 메인 루프가 해석 **전에** `rx_index1 = 0`, `RX_flag1 = 0`으로 수신을 다시 열어, ISR이 해석 중인 버퍼를 덮어씀. 또 1-1에서 넣은 길이 계산 상태(`calculate_cout`)가 STX에서 초기화되지 않아, 다음 패킷을 이전 패킷 길이로 판단해 버릴 수 있었음 |
| 수정 | ① 수신 플래그 해제를 해석이 **끝난 뒤**로 옮김 (인덱스 먼저, 플래그 나중) ② ISR은 `RX_flag1 == 1`인 동안 들어온 바이트를 버림 → 해석 중인 버퍼를 덮어쓰지 않음 ③ STX를 받을 때 `calculate_cout = 0` |
| 결과 | 보드 테스트에서 RGB LED 색 제어 정상, CLCD 등 다른 W 기능도 정상 (2026-11-20) |

```c
// ISR (HAL_UART_RxCpltCallback, USART1)
if (RX_flag1 == 1) { /* 해석 중 → 버림 */ }
else if (rx_index1 == 0) {
    if (rx_data1 == 0x02) { rx_buffer1[rx_index1++] = rx_data1; calculate_cout = 0; }
}
else { /* 1-1의 길이 기반 판별 */ }

// 메인 루프
if (RX_flag1 == 1) {
    /* ... 해석, 장치 제어 ... */
    rx_index1 = 0;   // 해석이 끝난 뒤에
    RX_flag1 = 0;    // 수신 재개
}
```

**배운 점:** ISR과 메인 루프가 같은 버퍼를 쓰면, "언제 버퍼를 넘겨주는가"를 정해야 한다. 메인 루프가 느려지는 기능(R 송신, 센서 측정)을 추가하면 기존에 드러나지 않던 경쟁 상태가 나타날 수 있다. 해석 중 들어온 패킷은 버려지므로, 연속 조작 중 중간 값 일부는 건너뛸 수 있다 (마지막 값은 반영).

## 2. 회로를 보고 코드로 대응한 부분

### 2-1. 서보 신호가 트랜지스터에서 뒤집히는 문제 → 타이머 극성으로 보정

| 항목 | 내용 |
|---|---|
| 회로 | PB7 → NPN 트랜지스터 Q2 → 컬렉터 10 kΩ 풀업(E5V) → 서보 신호 (EVB 회로도 p.4) |
| 문제 | NPN 스위치는 입력이 High면 출력이 Low → 서보에는 **반전된 펄스**가 도착 |
| 대응 | TIM4 CH2 출력 극성을 `TIM_OCPOLARITY_LOW`로 설정 → MCU 핀에서 미리 반전 → Q2에서 다시 반전되어 정상 펄스 (`main.c` `MX_TIM4_Init`) |
| 효과 | 3.3 V → 5 V 레벨 변환과 극성 보정을 부품 추가 없이 해결 |

### 2-2. JTAG 핀과 겹치는 입력 → SWD만 남기기

| 항목 | 내용 |
|---|---|
| 문제 | 엔코더 B(PA15)와 SW3(PB4)가 리셋 직후 JTAG 핀(JTDI, NJTRST) |
| 대응 | `__HAL_AFIO_REMAP_SWJ_NOJTAG()`로 JTAG를 끄고 SWD(PA13/PA14)만 사용 (RM0008 9.3.5, p.176) |

### 2-3. HDC1080 변환 대기 15 ms

| 항목 | 내용 |
|---|---|
| 관찰 | 드라이버 주석: "데이터시트 최대 7 ms인데 7 ms로는 값이 틀림 → 15 ms" |
| 원인 (데이터시트) | 온도·습도 연속 측정 모드(MODE = 1)에서는 변환 시간이 **온도 6.35 ms + 습도 6.50 ms = 12.85 ms** (HDC1080 데이터시트 p.5). 한 측정 시간(7 ms)만 기다리면 습도 변환이 끝나지 않음 |
| 결론 | 15 ms는 12.85 ms보다 길어 맞는 값. 경험적으로 찾은 값을 데이터시트로 설명할 수 있음 |

### 2-4. 송신을 장치별로 나눠 보내기

7개 장치를 50 ms마다 1개씩 보내 UART 송신(9600 bps, 패킷당 최대 약 10.4 ms)이 한 번에 몰리지 않게 했습니다 ([04 문서](04_firmware_implementation.md) 2절).

## 3. 소스·데이터시트 리뷰에서 발견한 이슈

> 아래 항목은 코드를 읽고 찾은 것입니다. **✅ 표시 항목만 수정했고**(2026-11-20, 1-1·1-2절), 나머지는 아직 수정하지 않았습니다. 보드에서 재현 여부를 확인한 항목은 따로 표시합니다.

### 3-1. 수신 패킷 처리 (우선순위 높음)

| # | 현상 (근거) | 영향 | 제안 |
|---|---|---|---|
| 1 ✅ | **ETX 값(0x03)으로 패킷 끝을 판단** (`HAL_UART_RxCpltCallback`). DATA는 이진값이라 0x03이 들어갈 수 있음 | 예: 엔코더를 3으로 쓰는 W 패킷 `02 57 45 04 03 00 00 00 03` → 5번째 바이트 `03`에서 패킷이 끝난 것으로 판단, 나머지는 다음 패킷 앞에 붙어 버려짐 | **수정 완료:** DATASIZE로 ETX 위치를 계산하고, 그 자리까지 받은 뒤 ETX 확인 (1-1절) |
| 2 ✅ | **수신 버퍼 범위 검사 없음** — `rx_buffer1[50]`에 `rx_index1++`만 함 | ETX가 오지 않으면(노이즈, 끊긴 패킷) 50바이트를 넘어 다른 변수를 덮어씀 | **수정 완료:** 길이가 50바이트를 넘거나 ETX 자리가 틀리면 버리고 다시 받음, 패킷 완성 후에는 해석이 끝날 때까지 바이트를 버림 → 인덱스가 ETX 자리를 넘지 않음 (1-1, 1-2절) |
| 3 ✅ | **해석 중 버퍼 덮어쓰기** — 메인 루프가 `rx_index1 = 0`으로 만든 뒤 `rx_buffer1`을 읽는 동안 ISR이 새 패킷을 같은 버퍼에 씀 | 연속 패킷이 오면 앞 패킷 데이터가 바뀐 채 해석될 수 있음 | **수정 완료:** 해석이 끝난 뒤 수신 재개, 그동안 온 바이트는 버림 (1-2절). 해석 중 온 패킷까지 살리려면 더블 버퍼 또는 링버퍼 |
| 4 | **장치별 길이 검사가 로그만 찍음** — ETX는 수정 후 ISR에서 검사하지만, 장치마다 정해진 길이(서보 2, RGB 3 등)와 맞는지는 `if (...) printf("DATABYTE_OK")`로 로그만 남김 | 장치에 맞지 않는 길이의 패킷도 그대로 적용 | 길이가 표와 다르면 패킷 버리기 |
| 5 | **오류 검출 없음** (체크섬·CRC 없음) | 블루투스 구간에서 바이트가 깨져도 알 수 없음 | ETX 앞에 체크섬 1바이트 추가 (앱과 함께 변경 필요) |

### 3-2. 데이터 해석·계산

| # | 현상 (근거) | 영향 | 제안 |
|---|---|---|---|
| 6 | **DAC 전압 계산이 3.3 V 기준** — `DAC_V = data × 3.3 / 4096` | DAC7512는 기준 전압 = VDD = **E5V** (EVB 회로도 p.2, DAC7512 데이터시트 p.11). 로그에 찍히는 전압이 실제의 약 2/3 | E5V 실측값으로 계산 (06 문서 측정 항목) |
| 7 ✅ | **CLCD 문자열 복사 루프가 1글자 빠짐** — `for (i = 15; i > 0; i--)`는 i = 15~1, 15글자만 복사 | 16글자를 보내면 1글자가 표시되지 않음 | **수정 완료:** `i >= 0`으로 16글자 복사, 보드에서 표시 확인 (1-1절) |
| 8 | **LED·스위치 바이트 순서가 R과 W에서 다름** — 교재 〈표 3〉은 `LED0|LED1|LED2|LED3` 순서. W는 첫 바이트를 `LED1_Pin`(PA6 = GPIO_LED0 = LED_R, EVB 회로도 p.1·p.3)에 써서 표와 같음. R은 `LED_data[3]`(LED_Y)부터, 택트 스위치도 `T_SW[3]`부터 보내 **표와 반대** | R로 보내는 LED·스위치 순서가 교재 표와 반대 | R 송신도 `LED_data[0]`, `T_SW[0]`부터 보내 표 순서에 맞춤 |
| 9 | **HDC1080 히터 켜짐** — `hdc1080_init(..., heater = 1, ...)` → 설정 레지스터 bit 13 = 1 (HDC1080 데이터시트 p.15) | 히터는 센서 시험·응결 제거용(데이터시트 p.9). 켜 두면 측정 온도가 실제보다 높게 나올 수 있음 | `heater = 0`. TC1047 값과 비교 측정으로 확인 (06 문서) |
| 10 | **float 변환에 포인터 형변환 사용** — `*(uint32_t*)&temp` | C 표준 strict aliasing 위반 (현재 컴파일러 설정에서는 동작) | `memcpy(&u32, &f, 4)` |
| 11 | TC1047 계산이 AVDD = 3.3 V로 가정 | AVDD 실제 값이 다르면 온도 오차 | AVDD 실측 또는 내부 기준 전압(VREFINT)으로 보정 |

### 3-3. 타이밍·구조

| # | 현상 (근거) | 영향 | 제안 |
|---|---|---|---|
| 12 | **메인 루프가 매번 HDC1080 측정** (15 ms `HAL_Delay`) | 루프 1회가 최소 약 16 ms → W 패킷 처리와 스위치 확인이 그만큼 늦어짐. 온습도는 350 ms마다만 송신하므로 매번 잴 필요 없음 | 측정을 350 ms(또는 1 s) 주기로, 또는 "측정 시작 → 15 ms 뒤 읽기"를 non-blocking으로 |
| 13 | **ISR에서 쓰는 변수에 `volatile` 누락** — `act_mode`, `TimerCount`, `rx_index1` | 최적화(-O2 등) 시 메인 루프가 변경을 못 볼 수 있음 (현재 Debug -O0에서는 동작) | `volatile` 추가 |
| 14 | **ADC DMA 인터럽트가 매우 잦음** — 3채널 1회 94.5 µs마다 반/완료 인터럽트 → 초당 약 21,000회 | 콜백은 비어 있지만 HAL 핸들러 호출 자체가 CPU 시간을 씀 | 타이머 트리거로 샘플링 주기를 낮추거나(예: 1 kHz) DMA 인터럽트 비활성화 |
| 15 | 모든 인터럽트 우선순위가 0 | 현재는 콜백이 짧아 문제없지만, 엔코더 펄스와 UART 수신이 겹치면 처리 순서를 제어할 수 없음 | UART RX > EXTI > TIM2 > DMA 순으로 우선순위 분리 |
| 16 | USART2 수신 콜백은 있지만 `HAL_UART_Receive_IT(&huart2, ...)` 시작 코드가 없음 | 죽은 코드 | 삭제하거나 PC 명령 입력 기능으로 완성 |
| 17 | `__io_putchar`가 `void` 반환 (`syscalls.c` 선언은 `int`) | 선언 불일치 | `int` 반환 |

### 3-4. 우선순위 요약

| 우선순위 | 항목 | 이유 |
|---|---|---|
